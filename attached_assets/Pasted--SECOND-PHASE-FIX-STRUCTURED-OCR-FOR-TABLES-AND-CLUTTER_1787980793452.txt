# 2. CHANGE THE OCR PIPELINE FROM "TEXT ONLY" TO "STRUCTURE-AWARE"

Inspect the current OCR implementation and determine the best way to preserve positional information from OCR.

The OCR stage should retain, whenever the OCR engine provides it:

* Recognized text
* Bounding box
* X position
* Y position
* Width
* Height
* Confidence
* Reading order

Do NOT immediately convert all OCR detections into:

`" ".join(...)`

or another flat string.

Once positional information is discarded, it becomes extremely difficult to reconstruct tables and multi-column layouts.

Preserve the OCR regions internally until layout analysis is complete.

---

# 3. TABLE DETECTION

Implement proper table-aware processing.

When the image appears to contain a table, determine:

* Where the table begins and ends.
* Number of rows.
* Number of columns.
* Header row, if present.
* Which OCR detection belongs to which cell.
* Empty cells.
* Numeric/currency cells.

Use the existing project architecture and dependencies where possible.

If OpenCV/table-line detection is appropriate, use it.

If the existing OCR engine's bounding boxes can be used to reconstruct cells, use those.

If grid lines are present, do not allow the OCR engine to simply treat the table as unrelated text regions.

The final internal representation should preserve something conceptually like:

```text
TABLE
  Row 1:
    Column 1: Item
    Column 2: Quantity
    Column 3: Price

  Row 2:
    Column 1: Apple
    Column 2: 2
    Column 3: ₹100

  Row 3:
    Column 1: Mango
    Column 2: 3
    Column 3: ₹150
```

Do NOT flatten this prematurely.

---

# 4. EMPTY CELLS MUST BE PRESERVED

This is important.

Suppose the original table is:

| Item  | Quantity | Price   |
| ----- | -------- | ------- |
| Apple | 2        | ₹100    |
| Mango |          | ₹150    |
| Rice  | 5 kg     | ₹320.50 |

The empty Quantity cell in the Mango row must remain empty.

Do NOT shift ₹150 into the Quantity column.

Do NOT assume that because a cell has no OCR text, the next detected value belongs to that column.

The positional relationship between cells is more important than simply concatenating OCR words.

---

# 5. MULTI-COLUMN DOCUMENTS

The same principle must apply to documents with multiple columns.

For example:

COLUMN 1:

* Item A
* Item B
* Item C

COLUMN 2:

* Item D
* Item E
* Item F

Do NOT read:

A → D → B → E → C → F

unless that is genuinely the document's reading order.

Use bounding-box positions and layout analysis to determine logical reading order.

---

# 6. CLUTTERED RESTAURANT MENUS

This is one of the most important real-world use cases for AksharAlly.

A menu may contain:

* Section headings
* Food names
* Descriptions
* Prices
* Multiple columns
* Decorative elements
* Vegetarian/non-vegetarian symbols
* Different font sizes
* Images
* Large spacing
* Dotted lines between items and prices

The system must understand spatial relationships.

For example, if the image visually represents:

STARTERS

Paneer Tikka ................ ₹220
Veg Manchurian ............. ₹180

MAIN COURSE

Paneer Butter Masala ....... ₹250
Dal Tadka .................. ₹180

the extracted structure should remain:

```text
STARTERS
Paneer Tikka — ₹220
Veg Manchurian — ₹180

MAIN COURSE
Paneer Butter Masala — ₹250
Dal Tadka — ₹180
```

It should NOT become:

```text
STARTERS
Paneer Tikka
₹220
Veg Manchurian
₹180
MAIN COURSE
Paneer Butter Masala
₹250
Dal Tadka
₹180
```

if the system can determine the item-price relationship from their spatial positions.

And absolutely do NOT produce:

```text
Paneer Tikka ₹180
Veg Manchurian ₹250
...
```

because of incorrect positional association.

---

# 7. ITEM → PRICE ASSOCIATION

For menus, use the spatial layout to associate prices with the correct items.

Prices are often:

* Far to the right of item names.
* Separated by dots.
* In another aligned column.
* On the same horizontal line.
* Sometimes on a second line.

Use bounding boxes and relative X/Y positions rather than OCR sequence alone.

The goal is:

**Item + Description + Price = one logical menu item**

when the image supports that relationship.

---

# 8. CURRENCY HANDLING

The previous validation showed cases where:

`₹220`

became:

`%220`

or the currency symbol disappeared.

Investigate why this is happening.

Do NOT simply blindly replace every `%` with `₹`.

That could corrupt legitimate percentages.

Instead:

* Inspect OCR confidence.
* Inspect the OCR language configuration.
* Inspect preprocessing.
* Determine whether the symbol is being misrecognized because of image quality, preprocessing, or OCR configuration.
* Apply a context-aware correction only when it is safe.

For example, if a detected token is immediately associated with a menu price and the OCR result is `%220`, investigate whether it is a likely currency-symbol recognition error.

Do not hallucinate currency symbols where they do not exist.

Also preserve:

* ₹
* Rs
* INR
* decimal prices
* commas in prices
* quantities
* percentages
* units

accurately.

# 10. FIX THE SIMPLIFY + FORMAT BRANCH

This is mandatory.

The current validation found that the Simplify + Format branch sends OCR text to Gemini and asks it to rewrite it as simplified prose.

That is unsafe for structured content.

Change this behavior.

The simplifier must follow this rule:

> **Simplify the language, but never destroy the information structure.**

For ordinary paragraphs:

* Break long sentences.
* Make them easier to read.
* Preserve meaning.

For headings:

* Keep them as headings.

For lists:

* Keep them as lists.

For tables:

* Keep rows and columns.

For menus:

* Keep sections and item-price relationships.

For numbers:

* Preserve them exactly.

For prices:

* Preserve the correct item-price relationship.

For names:

* Do not replace proper names with vague alternatives.

---

# 11. NEVER ASK GEMINI TO "JUST RETURN SIMPLIFIED PROSE"

Do not use a generic instruction such as:

"Rewrite this text in simple prose."

That is precisely what can destroy tables and menus.

If Gemini is used for simplification, provide it with structured content and explicitly require the structure to be returned.

For example, conceptually:

```text
{
  "type": "table",
  "headers": [...],
  "rows": [...]
}
```

or:

```text
{
  "type": "menu",
  "sections": [
    {
      "name": "Starters",
      "items": [
        {
          "name": "Paneer Tikka",
          "description": "...",
          "price": "₹220"
        }
      ]
    }
  ]
}
```

Use the format that best fits the existing architecture.

The important thing is that **the relationship between pieces of information must survive simplification.**
