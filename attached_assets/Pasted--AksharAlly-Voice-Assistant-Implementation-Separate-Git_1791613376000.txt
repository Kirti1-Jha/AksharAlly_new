# AksharAlly — Voice Assistant Implementation (Separate Git Branch)

## Project Context

I am developing **AksharAlly**, an AI-powered, dyslexia-friendly reading companion supporting English, Hindi and Marathi.

The existing application uses:
- **Frontend:** Flutter (`aksharally_ui`)
- **Backend:** Python Flask (`backend`)
- **OCR:** Existing multilingual OCR pipeline
- **Text processing:** Existing text formatting and text simplification modules
- **Text-to-speech:** Existing reading and speech functionality
- **Reader:** Existing reading screens with synchronized word/sentence highlighting
- **Other functionality:** Firebase authentication, library and saved reading content, accessibility settings, and existing API integrations

The repository may contain unused duplicate folders or older implementations. Identify the active Flutter application and backend before making any changes. Do not assume that every similarly named folder is in use.

## Main Objective

Implement a voice assistant for AksharAlly with two capabilities:

**Phase A — Voice Commands**
- Read the current text or page aloud.
- Pause, resume, stop and repeat reading.
- Increase or decrease the font size.
- Change background and text colours using supported voice commands.
- Display the recognized speech so the user can verify what was heard.
- Provide a visible microphone/listening indicator.
- Support English, Hindi and Marathi where the device's speech services allow it.

**Phase B — Conversational Reading Assistant**
- Let users ask questions about the currently displayed passage.
- Explain difficult words and paragraphs in simpler language.
- Speak the explanation aloud.
- Allow users to repeat an explanation.
- Preserve the original passage without overwriting it with an AI-generated explanation.
- Support English, Hindi and Marathi where feasible.

The two phases must remain separate so Phase A can work without an AI API.

## STEP 3 — Implement Phase A: Voice Commands

### Speech recognition

Use Flutter's `speech_to_text` package if it fits the existing architecture and is not already available.

- Request microphone permission appropriately.
- Display listening, processing, success and error states.
- Show the recognized speech.
- Allow users to stop listening.
- Handle unavailable speech services, denied permissions, silence, timeouts and recognition errors.
- Avoid continuous background listening.
- Ensure the microphone does not remain active unexpectedly.
- Support selecting English, Hindi or Marathi where supported by the device.
- Do not silently switch the selected language.

### Command processing

Implement a dedicated command/intent handler that is separate from UI widgets.

Support commands such as:

- "Read this page."
- "Pause reading."
- "Resume reading."
- "Stop reading."
- "Repeat that sentence."
- "Increase font size."
- "Decrease font size."
- "Change background colour."

Add suitable equivalents for Hindi and Marathi where feasible.

Use deterministic, rule-based command matching initially. Do not call an AI API to interpret simple commands.

If a command is ambiguous or unsupported, ask the user to repeat it or show a clear message rather than executing an unrelated action.

### Reader integration

- Reuse the existing reader and TTS controllers.
- Read the currently displayed content, not an unrelated or previously opened passage.
- Use the existing playback and highlighting logic wherever possible.
- Keep manual buttons functional.
- Prevent duplicate commands from executing twice.
- Avoid overlapping speech playback.
- Ensure changing the current document cancels stale playback and prevents commands from affecting the previous document.
- Preserve the existing text and its language.

### Accessibility and interface

Add a simple, consistent voice-assistant interface that matches the current AksharAlly design.

Include:
- A microphone control.
- Clear listening status.
- Recognized speech.
- A way to stop listening.
- A clear error or unsupported-command message.

Use accessible labels and appropriate touch-target sizes. Do not redesign unrelated screens.

### Phase A acceptance criteria

Phase A is complete only when:

- Microphone permissions and errors are handled.
- Speech recognition works on the available test device.
- Supported commands trigger the correct actions.
- Reading, pause, resume, stop and repeat work correctly.
- Font and colour commands update the actual settings.
- Existing manual controls continue working.
- TTS and highlighting behave consistently with the existing implementation.
- Unsupported commands fail safely.
- The application builds and relevant analysis/tests pass, or remaining environment blockers are clearly documented.
