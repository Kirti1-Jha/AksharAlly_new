# AksharAlly — Phase 1: Voice Assistant Audit, Git Safety and Implementation Preparation

## Objective

Prepare the existing AksharAlly Flutter project for a phased implementation of the redesigned login/register experience, default welcome message, Indian English text-to-speech, and unified first-time onboarding.

This is **Phase 1 only**. The objective is to inspect the repository, verify the active branch, understand the existing architecture, establish a baseline, and produce an actionable implementation report.

Do not implement the full feature set in this phase.

## 1. Mandatory Git Branch and Repository Safety

The required working branch is:

`feature/voice-assistant`

The active Flutter application is located in:

`aksharally/aksharally_ui`

First inspect:
- The current working directory and repository root.
- The active Git branch.
- Local and remote branch names.
- Git working-tree status.
- Existing uncommitted and untracked changes.
- Recent commits on `feature/voice-assistant`.
- Whether the local branch tracks `origin/feature/voice-assistant`.

### Strict Git rules

1. All subsequent implementation work must remain on `feature/voice-assistant`.
2. Do not switch to `main`, merge into `main`, or start implementation on another branch.
3. If the current branch is already `feature/voice-assistant`, stay on it.
4. If the branch is different, STOP before switching branches or changing files. Report the current branch and explain what must be done to return to the required branch safely.
5. Never discard, overwrite, reset, stash, or revert existing work without explicit approval.
6. Do not run destructive commands such as `git reset --hard`, `git clean -fd`, or forced checkout operations.
7. Do not merge unrelated Replit changes into this branch.
8. Do not push or merge anything during Phase 1.
9. Do not change Git remotes, credentials, or repository permissions.
10. Do not create duplicate branches or commits just to make the workflow appear complete.

If the working tree contains uncommitted changes, inspect them without modifying them. Identify which files are already changed and ensure that any later implementation can preserve those changes.

## 5. Prepare the Implementation Plan

Based on the actual repository, propose the smallest safe implementation sequence for the following future requirements.

### Phase 2: Welcome message and Indian English TTS

- Play the welcome message by default whenever the login/register screen opens.
- Default English speech to Indian English, preferring locale `en-IN`.
- Verify available voices where supported.
- Preserve appropriate Hindi and Marathi voice selection.
- Provide replay and safe fallback behaviour.
- Avoid duplicate or overlapping TTS playback.

### Phase 3: Login/register voice control

- Add a compact, visible, clickable voice-assistant toggle in the top-right corner.
- Keep the authentication interface clean and responsive.
- When enabled, support spoken instructions, field labels, button labels, and relevant validation messages.

### Phase 4: Unified first-time onboarding

- Use the same onboarding flow for email/password registration and Google sign-in.
- Collect the user's profile, self-reported reading-support preferences, reading languages, and reading goals.
- Allow users to skip optional or sensitive questions.
- Persist progress so incomplete onboarding can be resumed.
- Send returning users with completed onboarding directly to the home screen.

### Phase 5: Global accessibility settings

- Let users configure typography, text size, spacing, colours, reading assistance, and voice preferences.
- Preview the selected appearance.
- Persist settings using the existing architecture.
- Apply settings throughout the application without breaking existing reading features.

### Phase 6: Integration and verification

- Verify authentication routing, profile persistence, TTS behaviour, voice selection, onboarding recovery, and existing functionality.
- Run relevant tests, Flutter analysis, and available build checks.

For each phase, identify:
- The exact files likely to change.
- Dependencies on previous phases.
- Important implementation risks.
- The smallest independently testable deliverable.
- A suitable Git commit boundary.

Do not implement these future phases yet.
