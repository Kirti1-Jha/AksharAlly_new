# FEATURE 4 — ACCESSIBILITY SETTINGS: APPLY NOW AT TOP

## Current problem

The Accessibility Settings screen currently has an "Apply Now" button only at the bottom.

This creates a bad UX because the user has to scroll to the bottom every time they make a change.

## Required behavior

When the user makes ANY manual accessibility/settings change that has not yet been applied:

Show an "Apply Now" action at the TOP of the settings screen as well.

The top Apply Now action should become visible/enabled only when there are unapplied changes.

Examples of changes that should trigger it:

* Font selection
* Font size
* Letter spacing
* Line spacing
* Word spacing
* Text color
* Background color
* Reading mode
* Dyslexia-friendly settings
* Any other accessibility setting already supported by the application

Do NOT create a second independent settings state.

The top and bottom "Apply Now" buttons must operate on the SAME pending changes.

For example:

User changes:
Font → OpenDyslexic
Font size → 20
Background → cream

Then:

TOP:
[ Apply Now ]

and bottom:
[ Apply Now ]

Both buttons should apply exactly the same pending settings.

Once the user taps either Apply Now button:

* Apply the changes.
* Persist them using the application's existing settings persistence mechanism.
* Update the UI wherever necessary.
* Remove/disable the top Apply Now action because there are no longer unapplied changes.
* Keep the bottom button behavior consistent with the existing implementation.

If the user changes another setting afterward, the top Apply Now action should become available again.

## Important implementation detail

Do NOT duplicate the settings state.

Find the existing state/model/provider/controller used by the Accessibility Settings screen.

Use a single source of truth such as:

currentAppliedSettings
+
pendingSettings

or whatever equivalent architecture already exists.

Determine whether settings are currently managed through:

* Provider
* Riverpod
* Bloc/Cubit
* setState
* ChangeNotifier
* another existing state-management solution

and follow the existing architecture.

Do NOT introduce another state-management framework just for this feature.

## UI requirements

The top Apply Now action should be clearly visible but should not permanently occupy excessive space.

A good implementation could be:

* A compact action bar directly below the AppBar, OR
* A sticky action area at the top of the scrollable settings content.

Follow the existing AksharAlly visual design.

The action should clearly communicate that there are unapplied changes.

Example:

"Changes not applied"
[ Apply Now ]

The exact design can follow the existing UI.

The bottom Apply Now button should remain because some users may naturally reach the bottom.
